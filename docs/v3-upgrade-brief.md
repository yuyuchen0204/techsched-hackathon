## 1. 本轮目标与范围

## 2. 必须保留的业务规则

### 2.1 时间与维修目录

- 预约窗口表示允许上门并开始服务的时间：`window_start <= service_start <= window_end`。
- 允许提前到达后等待；维修可以在窗口结束后完成，但不得违反下班时间、已锁定休息、后续工单等约束。
- 迟到与风险的截止点统一为 `window_end`，不能误用窗口开始时间。
- 默认使用 `Asia/Singapore`，时间持久化和比较采用统一规则，界面展示当地时间。
- CSV 为“维修类别—具体问题—复杂度—固定维修时长”的权威来源。默认路径 `data/reference/repair_object_problem_database.csv`，支持 `REPAIR_CATALOG_PATH`。
- 读取实际 CSV 列名并适配，不假定输入文件一定使用某组英文字段。
- 模型可以匹配、查询、追问，但不能编造目录项目、复杂度或时长。
- 技师技能必须达到问题复杂度要求；高技能不自动意味着工时更短。
- 工单保留目录和服务时长快照。目录或旁路预测更新不追溯修改既有工单。

### 2.2 优先级

数字越小越紧急。普通订单基础优先级为 P3，模拟付费加急为 P1；P1 可以因风险升级为 P0。有效优先级取基础优先级与当前有效风险中更紧急的一项。

| 条件 | 风险优先级 |
| --- | --- |
| 超过窗口结束且尚未开始服务 | P0 |
| 技师取消，距离窗口结束不足 30 分钟 | P0 |
| 客户投诉迟到，经事实核实已超时且未开始服务 | P0 |
| 预计开始服务时间超过窗口结束 | P1 |
| 技师取消，距离窗口结束 30—120 分钟，含端点 | P1 |
| 无预计迟到，距窗口结束不超过 30 分钟，且尚未开始服务 | P2 |
| 技师取消，距窗口结束超过 120 分钟 | P2 |
| 其他情况 | P3，仍受基础优先级下限约束 |

多个条件重叠时取最紧急风险。风险解决后可以重新计算，不永久累加。已开始服务、已完成、已取消的订单不再触发“尚未开始服务”的重复调度。

态度、质量等非排班投诉进入人工处理，不因投诉字样自动升级调度优先级。安全事件另见第 9 节。

### 2.3 调度权限和自动执行

| 目标订单 | 允许的调度行为 | 自动执行/审批 |
| --- | --- | --- |
| P3 | 零扰动分配 | 合法方案决策得分 >70 可自动执行；否则转人工评审 |
| P2，已有有效分配 | 保留现有分配，可寻找最多 3 个备用候选 | 不因为备用候选更优而自动换人 |
| P2，没有有效分配 | 允许零扰动补派 | 得分 >70 可自动执行；否则转人工评审 |
| P1 | 最多影响 2 张尚未出发的 P3 | 合法方案决策得分 >70 可自动执行，包括影响 1—2 张 P3 的情况；否则转人工 |
| P0 | 最多影响 5 张尚未出发的 P2/P3 | 零扰动且得分 >70 可自动执行；影响 1—5 张时无论得分都需人工审批；零扰动低分也需人工 |

- 阈值是严格大于 70；得分 70 不满足自动执行条件。得分不是成功概率。
- 决策得分为所有新增或改变分配的得分最小值，不是平均值或仅目标订单得分。
- P1 不得移动其他 P2/P1/P0；P0 不得移动其他 P1/P0。
- 所有等级都不得打断已出发、已到达或服务中的订单。忙碌技师可以在锁定任务之后接新任务。
- 目标订单本身在尚未出发时允许按其规则重新分配，不计入“其他受影响订单”数量。
- 硬约束不满足或超出权限的方案不得通过普通人工审批绕过。可以创建人工异常处理事项，但不提供“强制提交非法方案”按钮。
- 候选方案最多展示 3 个真实不同且合法的完整方案，不足 3 个不补造。P2 备用技师与完整方案列表分开。
- 不新增未经要求的“出发前 15 分钟冻结”等政策。

### 2.4 扰动计数与迟到恢复

- 在同一基线版本上，除目标订单之外，原有有效订单的技师或计划开始服务时间发生变化即计入影响。
- 以订单 ID 去重，同一订单换人并改时间只计一次；时间变化达到 1 分钟计入。
- 所有连锁变化都计入。不能丢弃被挤走订单，也不能分拆方案或更换目标标签逃避上限。
- 只有路线变化、技师和开始时间都不变时不增加订单计数，但必须验证路线可行性。
- 被移动的其他订单仍须满足原预约窗口。
- 已经迟到的目标订单可以产生恢复 ETA；保留原窗口和迟到事实，不能伪装按时，也不能连带放宽其他订单窗口。
- 迟到恢复仍遵循审批权限。可按政策执行恢复方案并告知客户，不强制等待客户再次确认已批准范围内的恢复；客户拒绝时再处理改期或未出发取消。

### 2.5 取消、失效和并发

- 客户未出发前可取消任何优先级的订单。取消后需求终止、释放占用、关闭风险和备用候选、使关联待审批方案失效；保留历史，不删除订单。
- 已出发、已到达、服务中不能客户取消；完成等终态不能重复取消。
- 技师取消或请假意味着资源不可用，不意味着客户需求取消。先如实使无效分配失效，再对受影响需求进行恢复。
- 客户取消与技师出发使用原子状态转换，二者不能同时成功。
- 旧审批、旧 Agent 结果不能复活取消订单或覆盖新状态。
- 删除中间订单后重新计算前驱到后继的路线，不能继续经过被取消地点。
- 提交时重新检查订单、技师、方案和模拟会话版本，事件和提交须幂等。

## 3. 总体架构与三端一致性

保留现有三个逻辑角色，可调整名称：

1. **Customer / Understanding Agent**：目录查询、需求澄清、历史信息确认、可行时间协商、客户反馈。
2. **Scheduling Agent**：查询资源、选择搜索策略、试排、权限内修复、根据工具结果调整、提交方案或请求审批。
3. **Risk / Recovery Agent**：调查风险和异常、主动转人工、动态休息判断、跟进未解决任务。

确定性组件负责：订单状态机、优先级和权限计算、时间计算、路径与可行性验证、得分、版本校验、原子提交、事件分发及任务预算。

- 不要求每个事件依次调用三个 Agent。简单事件走最短有效路径。
- 不为目录查询、地图或评分简单增加一批命名 Agent；将其作为工具即可。
- 后端为状态唯一来源。三端通过现有轮询、SSE 或 WebSocket 同步，优先复用已实现机制。
- 对同一技师动作，人工点击和模拟器只允许一个有效驱动者，避免重复推进状态。
- 演示会话、时钟、种子和版本统一。重置后旧异步任务不得写回新会话。
- 三端共享业务状态，但按身份限制可见内容；客户不能查询其他客户或技师全天位置，技师只看工作所需信息。

## 4. 客户手机端改造

### 4.1 对话与问题联想

- 手机优先响应式布局，输入、建议项、确认卡片和按钮在窄屏可用。
- 问题联想区域只显示目录中的具体维修问题，不混入地名、商场和地图按钮。
- 问题和地址分别采集。模型需要时调用目录工具，存在会影响分类的歧义时提出针对性问题。
- 不机械重复已明确的信息，不强迫每位客户经历相同的问题顺序。
- 聊天中提供明确“转人工”按钮；识别自然语言转人工请求。
- 转人工保留已有上下文，避免让客户重新填写全部信息。

### 4.2 地址弹窗

支持邮编或具体地名搜索，展示搜索结果供客户选择；支持地图选点；最后填写 unit/楼层房号等详细信息。

建议保存以下语义字段：

`formatted_address, postal_code, building_name, street_address, unit_number, latitude, longitude, source, confirmed_at`。

- 经纬度供路线计算，完整地址和 unit 供上门使用，两者都保留。
- unit 为确认步骤；确实不适用时允许明确选择“不适用”，不要要求填写假数据。
- 搜索或逆地理编码不能解析的地址信息由客户补充，禁止 LLM 生成虚构邮编或坐标。
- 地图选点和搜索结果需要最终确认；错误地点可以修改。
- 地理服务通过适配器接入。离线模式使用明确标注的可搜索本地地址数据，不将无法识别的任意地址假装解析成功。
- 服务范围不匹配时提示重新选择或转人工，不默认生成超范围派单。

### 4.3 独立订单详情页

创建订单后进入可再次访问的订单详情页，展示订单号、问题、完整地址、预约窗口、当前状态、预计开始时间、技师、当前处理进展。

提供：

- 投诉：填写类型与内容，产生投诉事件并显示受理状态。
- 模拟加急：在原订单上将基础优先级提升至 P1，不重复建单，不降低已因风险处于 P0 的订单。
- 取消：未出发可用；后端校验最终状态；成功后显示取消状态。
- 转人工：展示是否等待接手、是否已有回复。
- 评价：完成后填写服务评价，支持结构化原因和文字说明。
- 技师状态与跟踪：未出发展示状态，出发后展示与本订单相关的位置、路线和 ETA；结束或取消后停止实时跟踪。

重复点击模拟加急不得重复收费或重复创建事件；已经执行或终态订单不再提供没有意义的加急操作。

### 4.4 预约协商

- 调用只读试排工具推荐真实可行窗口，客户选择后再次验证；推荐不等于资源预留。
- 客户不接受最早时段时，Agent 可尝试其他技师或其他窗口，并说明响应时间和调度影响。
- 不能为了得到更好方案自动改变客户预约窗口。
- 对已存在订单的改期，本轮采用“生成待人工确认的改期请求”默认方式；审批前保持旧窗口和有效安排，后续提交仍需完整验证。
- 若客户要求“某时刻前维修结束”，需要澄清这是额外完成时间要求。MVP 记录并转人工，不偷换既有窗口定义，也不自动承诺。

## 5. 模拟技师手机端

### 5.1 页面与身份

- 实现可操作的手机端，可在演示身份选择器中切换技师；清楚标注模拟身份。
- 显示今日 Timeline：通勤、服务、休息、不可用时段。
- 展示下一单问题、预约窗口、完整地址、unit、路线及相关服务记录摘要。
- 地图显示目的地与路线。真实导航 App 跳转可选，不作为基础演示依赖。

### 5.2 操作与状态

至少提供“已出发”“开始服务”“已结束”。可复用现有“已到达”状态。

- 已出发：记录 actual_departure_at，进入 EN_ROUTE 并锁定。
- 已到达：若系统有该状态，记录到达并处理提前等待。
- 开始服务：记录 actual_service_start_at，进入 IN_PROGRESS；检查时间和状态一致性。
- 已结束：记录 actual_service_end_at，进入 COMPLETED，触发后续 ETA 和资源更新。
- 实际服务操作不应强迫技师伪造符合计划的时间。若实际发生违规提前开始或超时，应记录事实并标记异常，而非篡改事实；自动模拟器遵守计划窗口和合法状态转换。
- 状态推进不能跳过必需数据。手工模式缺失开始时间时要求补录有依据的时间或标记数据无效，不能用出发时间代替维修开始。
- 不提供回退按钮解除已出发锁定；纠错走人工审计流程。
- 允许切换手动演示和自动模拟模式，切换时保留已发生事实，避免双重事件。

### 5.3 临时请假

- 输入不可用开始和结束时间、原因，可从当前时间开始。
- MVP 将该操作视为技师申报已确定的不可用事实，不等待审批才阻止继续派单。
- 对尚未出发的受影响分配立即标记失效，保留客户需求，逐单重新判断优先级并启动恢复。
- 若与当前执行任务重叠，创建人工异常事项，不自动中止、解锁或删除执行任务。
- 显示哪些订单受影响以及当前处理状态；不得让一张被恢复订单掩盖其他未解决需求。

### 5.4 维修反馈

- 记录实际发现的问题、维修处理结果、备注及可选目录匹配。
- 原报修问题与实际诊断结果分别保存，不能覆盖原始报修历史。
- 记录实际起止时间、中断及异常标记，为旁路时长评估提供数据。
- 完成状态可以先保存，反馈不足时保留“待补充反馈”，不要让网络失败导致工单一直无法完成。

## 6. 调度后台与地图

### 6.1 简化界面

- 从正式业务首页删除 Inject event 按钮和相同性质的手动技术事件入口。
- 隐藏接口地址、模型供应商、调试参数等实现信息，放入开发设置。
- 精简数字卡片，默认保留待处理工单、风险工单、待人工处理、可用技师；可复用已有真正必要指标。
- 删除“所有人统一固定午休”的文案和固定区块生成逻辑，保留实际动态休息展示。
- 保留必要模拟时间控制；把批量场景加载和种子选择放入独立演示控制区。
- 保留人工审批、人工处理、Agent 活动、通知和订单/技师详情的可达入口。

### 6.2 地图交互

- 点击技师查看当前状态、任务和选中路线。
- 点击工单查看详情、窗口、优先级和处理状态。
- 显示当前位置、下一目的地及路线；避免所有路线同时铺满地图。
- 技师状态颜色覆盖空闲、通勤、服务、休息、不可用，并提供图例。
- 工单优先级和技师状态使用独立图例，辅以文字/图标，不能仅依靠颜色。

### 6.3 动态位置

- 根据后端模拟时钟、路线几何和已计划/已实际发生的行程推进位置，禁止随机飘动。
- 暂停时位置暂停；快进按业务时间推进；到达后停留在目的地。
- 开始位置和下一段行程相连，不瞬移回服务基地。
- 当前服务地点、当前坐标、下一目的地使用不同语义字段。
- 客户端和后台显示同一位置快照。取消、完成和会话重置及时结束旧跟踪。
- 区分路线几何、行程时间估计和实时交通。没有实时交通接口时标注模拟或静态估计，不声称实时路况。
- 保留实时路况/定位适配器扩展点，不把接入真实 API 作为本轮必需条件。

## 7. 动态休息：替换统一固定午休

### 7.1 已确定的默认解释

会议“午休时间删掉”解释为取消所有人统一固定午休；会议“智能判断是否需要午休”落实为按每位技师工作情况安排动态休息。不能删掉全部休息能力。

### 7.2 默认演示策略

在现有仓库没有更明确参数时，采用以下可配置演示默认值，并写明不是劳动法规或医学疲劳判定：

- 工作累计包含通勤和服务，明确记录的休息后重置；普通空闲不自动当作有效休息，需形成明确休息段。
- 累计工作达到 180 分钟时开始评估后续 90 分钟内的休息机会。
- 累计达到 240 分钟仍未安排有效休息时，创建高优先级人工关注事项。
- 默认休息 30 分钟，不伪装为固定每日统一 12:00 午休。
- 对可预测将达到评估阈值的技师允许提前试算候选时段，避免只能在来不及时处理。

这些参数用于支持确定性评估；Agent 结合上下文选择是否查询、何时安排和选择哪个合法时段，不凭空判断生理疲劳。

### 7.3 执行流程

1. 查询当天工作、通勤、休息及后续日程。
2. 调用评估工具获得事实、建议等级和候选搜索范围。
3. 查询可用空档并试算休息，检查位置、必要通勤和所有后续窗口。
4. 存在零扰动时段时，选择合适时段并请求提交。
5. 写入持久化休息区块，同时通知技师并同步 Timeline。
6. 无合法零扰动时段时转人工，附上冲突证据及可考虑的方案。

### 7.4 权限边界

- 本轮动态休息只允许零扰动自动安排，不能套用 P0/P1 订单权限去强行移动其他订单。
- 已提交休息是排班不可用区块；本轮不允许 Agent 自动缩短、取消或跨越它。
- 正在执行的通勤或服务不能被自动打断安排休息。
- 并发新订单与休息提交须校验同一日程版本，不能重叠成功。
- 通知失败不回滚已成功写入的休息，只重试通知。
- 重复扫描不反复生成相同休息或人工事项。
- 若旧系统已有真实明确确认的休息记录，迁移时保留；只替换默认固定模板生成机制。

## 8. 历史记忆与客户偏好

### 8.1 本轮必须提供基础历史库

历史信息虽然也出现在会议“未来展望”，本轮明确实现基础数据、查询和交互；长期个性化训练属于未来。

历史数据至少包含客户、已确认地址、历史工单、实际问题、技师反馈、客户评价、人工处理结论。

- 用稳定 customer_id/演示账号识别老客户，不能只用同名匹配。
- 客户端只读本人历史；技师只读与任务相关摘要；调度员按演示角色访问。
- 本轮优先采用结构化数据库查询，不强制引入向量库。
- 自由文本反馈作为数据，不作为可以覆盖系统规则的指令。

### 8.2 老客户信息确认

- 获取已确认的历史地址和电话，询问本次是否继续使用。
- 若客户本次已提供不同信息，先确认更新，不重复展示历史信息要求其改回。
- 支持“仅用于本次”或“保存为常用信息”的简单区分。
- 历史个人信息不因聊天中随意输入他人姓名或电话而暴露。

### 8.3 差评技师偏好

- 客户对某位技师的历史负面评价形成可解释软偏好，合法性和原有审批规则优先。
- 相近可行方案中优先其他人选；没有替代时解释情况或询问，不直接宣布无法服务。
- 区分技师态度/维修质量、调度迟到、平台问题，避免全部归咎于技师。
- 客户在本次订单明确拒绝某位技师时，记录订单级排除条件；排除后无可行资源则协商或人工处理，不能悄悄违反明确要求。
- 不默认形成永久全局黑名单；同一次明确拒绝不自动作用于所有未来订单。
- 本轮默认采用候选排序中的偏好/机会成本项，不随意重标原有 0—100 评分或阈值。记录偏好对选择的实际作用。

### 8.4 重复故障提示

- 查询同一客户、地址和尽可能同一设备的近期历史。
- 缺少设备标识时表述为“同类维修记录”，不要断言同一设备重复故障。
- Agent 可提醒客户已有相关历史，并给技师生成进一步排查提示。
- 默认使用可配置的 90 天历史窗口进行检索，不将检索命中自动当作诊断结论。
- 不自动提高复杂度、延长正式排班时长或认定维修根因。

## 9. 高危险识别与紧急协助

### 9.1 独立安全事件

建立独立 SafetyIncident/紧急事件语义，记录危险类型、客户原始描述、已知地点、处理状态、关联客户和可选工单。

- 危险等级与订单调度 P0—P3 分开。安全事件可以高优先级通知人工，但不自动授权派单越权。
- 识别到可信高危险描述后优先给出审核过的简短紧急提示和联系入口，暂停普通加急营销与冗长表单。
- 不把紧急联系简化为“付费升 P1”或“派最近维修师傅”。
- 可结合确定性触发与 LLM 上下文判断；避免只要包含“火”“电”等字就断定危险，保留否定、过去事件等语境。
- 模型不可用时保留保守的紧急联系入口和人工接管路径。

### 9.2 “帮我报警”按钮

- 符合会议要求提供该入口，附近明确说明“打开紧急联系电话，不会自动代为报警”或当前模拟行为。
- 默认不接真实报警 API。可使用设备拨号链接或明确标注的演示协助请求。
- 按危险类型配置适用的紧急联系渠道，不把所有情况交给同一号码。
- 如果要填入真实号码或具体应急指引，实施时核对新加坡相关官方来源并在配置文档保留来源；没有核实则不要编写号码。
- 打开拨号界面、用户确认已联系、外部确实受理分别记录，不能相互等同。
- 不在模拟模式中执行真实拨号或发送真实紧急请求。

### 9.3 紧急信息不完整

- 可先创建紧急事件或待补充草稿，保存已有信息，不等待所有普通字段齐全才展示紧急提示。
- 未具备可定位地址、明确服务需求等最低条件时，不创建可自动执行的维修分配。
- Agent 可选择先问紧急联系需要的信息，再补普通服务字段。
- 安全事件本轮由人工确认处理结果后关闭；LLM 不凭一句推测自动解除危险。
- 不生成要求客户操作危险设备的自由发挥式处置指令，使用审核模板并引导专业紧急服务。

## 10. 人工接管和审批必须区分

### 10.1 三种来源

- CUSTOMER_REQUEST：客户主动点击或提出。
- POLICY_REQUIRED：例如已有 P0 方案影响 1—5 张其他订单，需要审批。
- AGENT_ESCALATION：Agent 根据矛盾信息、超范围、工具失败、反复尝试无进展、复杂客诉或安全事件判断需要人工。

审批队列与人工处理队列可以共用页面，但语义和权限不能混为一谈。批准一个合法待审批方案不等于可以跳过硬约束。

### 10.2 人工处理工具

实现 `flag_for_human` 或等价工具，至少包含：

`customer_id, order_id?, incident_id?, category, urgency, reason_summary, evidence_refs, attempted_actions, unresolved_questions, suggested_next_action, idempotency_key`。

- 判断应有事实依据，不只使用模型自报 confidence。
- 对同一未解决事项去重，新的证据追加到已有事项；升级紧急程度而非无穷新建。
- 显示待接手、处理中、等待客户、已解决；记录负责人和处理结果。
- 人工能查看对话摘要、相关工具证据、订单和候选方案，并向客户端发送站内回复。
- 人工接管期间，Agent 暂停与人工相冲突的客户承诺和业务写入；允许更新事实与后台监测。
- 人工结束后可唤醒 Agent 继续未完成任务，但必须重新读取状态。
- 主动转人工不自动意味着订单升级，不重复生成付费加急。

## 11. Agent 的运行机制与工具契约

### 11.1 必须是真实的受限自主决策

Agent 接收业务目标、最新事实和允许的工具集合，根据工具结果决定下一动作。不要只将固定 if/else 流程包装成若干名为 Agent 的函数。

允许的行为示例：

- 分类不明确时查询目录并追问，而非盲目提交。
- 直接插入失败后阅读冲突原因，决定查询其他候选或进行权限内局部修复。
- 已发现所有候选技能不足时，不继续无意义重试相同时间安排。
- 客户拒绝某一窗口后试算其他方案，或提出具体待人工协调事项。
- 发现重复故障时主动查询相关历史并生成有证据的提示。
- 发现多个事实矛盾、重复失败或超出服务范围时主动转人工。
- 处理成功后停止，不为了展示调用更多工具而继续循环。

### 11.2 建议工具集

| 工具语义 | 作用 | 属性 |
| --- | --- | --- |
| search_repair_catalog | 查询目录、复杂度、固定时长 | 只读 |
| search_address / reverse_geocode | 地址搜索与坐标解析 | 只读 |
| get_customer_history | 查询已授权客户历史 | 只读 |
| get_order_context | 当前工单、风险、版本、关联事件 | 只读 |
| query_technicians | 技能、可用时间、位置和日程 | 只读 |
| get_travel_times | 路线时间估计及来源 | 只读 |
| simulate_insertion | 零扰动插入试算 | 只读 |
| search_local_repair | 权限内局部修复搜索 | 只读 |
| validate_plan | 完整方案、扰动、评分和审批判断 | 只读 |
| propose_alternative_windows | 查询其他可行窗口 | 只读 |
| evaluate_break_need | 工作与休息事实评估 | 只读 |
| simulate_break | 验证休息候选 | 只读 |
| create_customer_question | 创建结构化待回复问题 | 写入等待事项 |
| flag_for_human | 转人工并附证据 | 写入人工事项 |
| create_safety_incident | 保存紧急事件/草稿 | 写入事件 |
| submit_plan | 自动提交或创建合法审批 | 受保护写入 |
| submit_break | 零扰动提交休息 | 受保护写入 |
| notify_in_app | 创建站内通知 | 幂等写入 |

工具可以复用既有服务，不强制全部独立 HTTP 接口。工具执行前验证身份、参数和业务权限，不让 LLM 自报身份或自由扩大候选扰动上限。

### 11.3 结构化工具结果

工具返回 `status, snapshot_version, data, reason_codes, evidence_refs` 等可解释字段。

例如试排失败：

```json
{
  "status": "infeasible",
  "snapshot_version": 42,
  "reason_codes": ["SUCCESSOR_WINDOW_VIOLATION"],
  "data": {
    "conflicting_order_id": "J208",
    "predicted_service_start": "2026-09-20T16:20:00+08:00",
    "latest_allowed_start": "2026-09-20T16:00:00+08:00"
  }
}
```

- 区分确定不可行、搜索预算耗尽、暂时服务错误、数据不足和版本失效。
- 求解器超时或局部搜索没找到方案，只能说“本轮搜索未找到”，不能声称数学上无解。
- 参数非法与越权不是可通过反复随机重试绕过的错误。
- 工具返回只包含当前角色所需信息，不把整库和个人信息全部塞入模型上下文。

### 11.4 提交与事件

- 模型只选择候选和表达意图，后端政策引擎决定能否提交、是否审批。
- `submit_plan` 以方案 ID 和期望版本提交，不能直接接受模型任意拼写的“已验证”结果。
- 后端重新校验当前状态；审批通过时也须重新校验。
- 所有相关改动一次原子提交，通知在成功提交后发出。
- 时间窗修改、身份授权、取消限制均不由 Prompt 单独防护，必须落实到后端。

### 11.5 预算、等待与恢复

- 默认每次任务唤醒最多 12 次工具调用、最多 3 次不同策略的方案搜索；配置化并允许根据现有实现合理调整。
- 对临时网络错误最多进行少量有界重试；不要无限循环相同参数。
- 提交尝试、工具耗时和模型错误均记录。
- 明确终态：成功、等待客户、等待人工、已失效、未找到方案、技术失败。
- 等待客户或人工时保存任务后退出，不保持长时间 LLM 循环。
- 新事件到达后唤醒，重新获取事实和版本再决定动作。
- 实时 Agent 耗时不应让模拟时钟失控。提交时依据最新模拟时间校验；Demo 可由用户暂停时钟观察，不在后台隐式篡改时间。

### 11.6 无模型服务时

- 提供可运行的 mock 模式用于接口、页面和确定性测试，明确标注其为模拟行为。
- 真实 Agent 模式必须由模型根据实际工具返回选择后续行动；不得播放预写文本冒充实时推理。
- 模型服务失败时保留规则检查、人工处理和必要业务功能，并说明降级状态。

## 12. 持续任务、事件与通知

建议持久化 AgentTask：

`id, role, goal, customer_id?, order_id?, incident_id?, status, session_generation, snapshot_version, facts_summary, tried_plan_ids, evidence_refs, pending_question_id, human_case_id, tool_budget_used, wakeup_reason, created_at, updated_at`。

- 不保存或展示模型私有思维链。保存可核查事实、行动摘要、工具参数摘要和结果即可。
- 事件至少覆盖：客户创建/取消/加急/投诉/回复，技师出发/开始/完成/请假/反馈，休息提交，人工处理/审批，风险变化和会话重置。
- 为同一订单的恢复任务去重或合并新事件，防止多 Agent 同时提交冲突方案。
- 多张订单受到技师请假影响时，要记录恢复批次；每张目标订单按政策处理，并避免在同一事件中通过多个目标连续操作逃避扰动上限。
- 已提交方案后再次改变同一组订单须有新事实和可追踪原因，不能为了越过预算拆成多个事务。
- 通知记录送达状态和幂等键；站内通知是真实业务记录，外部短信默认为未接入。

## 13. 维修时长采集和旁路预测

### 13.1 本轮默认模式

`DURATION_PREDICTION_MODE=shadow`：正式排班继续使用 CSV 固定时长；历史模型只计算预测和误差，不改变正在使用的排班时长。

必须完成数据采集、可解释基线预测、评估报告或后台开发视图。暂不开发自动在线更新正式排班。

### 13.2 数据

- 实际服务时长以开始服务到完成为基础，排除可明确记录的中断；通勤和提前等待不得计入。
- 缺失时间、负时长、明显异常、无法区分中断的数据标记质量问题，不直接训练。
- 保留基准时长、预测时长、实际时长、问题分类、预测版本、预测发生时间和数据来源。
- 合成历史标记 simulated，实际人工录入标记来源，报告区分两者。
- 反馈中新增的实际问题不自动覆盖用于当时预测的原输入，避免事后信息泄漏。

### 13.3 轻量预测和验证

- 初版使用按具体问题分组的历史中位数等可解释方法；默认少于 5 条合格历史回退 CSV。
- 如需收缩估计或增加复杂度分组，保留清晰说明，不为比赛引入不必要模型训练。
- 按时间切分训练与评估，预测只能使用当时已完成记录，不用未来数据。
- 与 CSV 基准比较 MAE、有效样本数、回退比例；没有足够数据就说明，不编造提升。
- 定时或手动构建新预测版本，保留版本来源，不每条事件无审计地改动参数。
- 未来接入正式排班需独立启用、版本化并对新方案重新验证；本轮 UI 不提供随意切换到未实现生产模式的按钮。

## 14. 数据库与迁移

复用已有实体，按需要扩展，不为每个概念重复建表。至少覆盖以下语义：

| 实体/记录 | 必需信息 |
| --- | --- |
| Customer / Address | 稳定身份、历史联系方式、详细地址及确认 |
| Order | 原问题、目录/时长快照、窗口、基础/有效优先级、状态、版本 |
| Assignment / Plan | 技师、计划时间、锁定、基线版本、候选与审批 |
| TechnicianAvailability | 班次、休息、请假及不可用原因 |
| ExecutionEvent | 出发、到达、服务开始、结束及事件来源 |
| ServiceReport | 实际问题、处理结果、中断和维修反馈 |
| CustomerFeedback | 评价对象、原因、内容、处理状态 |
| HumanCase / Approval | 接管事项与方案审批，分别表达权限语义 |
| SafetyIncident | 危险事件、已知信息、人工处理状态 |
| AgentTask / ToolTrace | 目标、状态、工具调用、证据、预算、等待条件 |
| Notification | 接收对象、渠道、状态、幂等键 |
| DurationObservation / ModelVersion | 时长样本、质量标记、预测及评估版本 |

- 迁移兼容历史缺少 unit、客户身份或实际起止时间的情况，标记待补充，不能编造真实数据。
- 将现有散落地址字符串迁移为可逐步补充结构，不破坏历史展示。
- 适当增加外键、状态和时间检查、查询索引、幂等唯一约束。
- 通用业务记录保留 created_at/updated_at；涉及仿真的事件记录明确业务模拟时间和系统审计时间。
- 数据迁移、模拟数据重建与生产数据重置分开，不在每次启动时自动清空数据库。

## 15. 接口与前后端集成

沿用现有 API 风格，提供对应能力而非强制重命名全部接口。前后端共享或生成类型，避免各端分别推断订单状态。

建议能力：

- 客户：当前身份、历史信息确认、地址搜索、订单列表/详情、投诉、加急、取消、评价、人工对话。
- 技师：今日 Timeline、下一单详情、出发、开始服务、完成、请假、维修反馈、休息通知。
- 调度：地图快照、订单/技师详情、审批、人工事项处理、Agent 任务和活动记录。
- 演示：时钟、加载场景、模式切换、重置及场景执行结果。
- 内部 Agent 工具：读取事实、只读试算、提交、等待事项、通知。

错误码至少能表达 `INVALID_STATE, VERSION_CONFLICT, POLICY_VIOLATION, DATA_INCOMPLETE, NOT_FOUND, FORBIDDEN, TOOL_UNAVAILABLE, SEARCH_BUDGET_EXHAUSTED`。

前端应展示可理解的提示并刷新最新状态；不要把原始堆栈或接口密钥展示给用户。

## 16. Agent 活动面板

必须由实际任务与工具日志驱动，展示：

- 当前目标和关联订单。
- 当前动作及使用的工具。
- 关键输入摘要和返回事实。
- 失败原因及接下来的行动摘要。
- 方案影响数量、政策判断和审批状态。
- 最终执行结果或等待事项。

要求：

- 清晰区分准备调用、已调用、已返回、已验证、已提交。
- 试算不显示为已执行；创建审批不显示为已分配。
- 不展示模型内部思维链；不输出完整个人信息或密钥。
- 可以显示总调用次数和耗时，但不将调用越多作为越智能。
- 同一异常在不同数据条件下，应能看到不同后续行动，例如直接补派、局部修复、主动转人工。
- 回放模式与实时模式明确标注，不能将过去日志冒充当前真实调用。

## 17. 模拟数据与演示场景

### 17.1 以负载和约束设计数据

- 技师数量、订单数量、技能分布、地理分布、窗口宽度、服务时长和通勤共同决定难度。
- 检查现有数据规模后，至少提供宽松、繁忙、资源不足三种固定种子场景。
- 可从 8—12 名技师开始设计，但订单数必须结合实际 CSV 时长和班次计算，不照抄固定数量。
- 工作负载指标优先使用服务与通勤占可用时段比例，注明是否扣除休息；额外检查技能和时间窗口瓶颈。
- 初始化正常场景应有可行安排；刻意构造的资源不足场景要说明其目的。
- 不通过硬编码“这个场景一定调用某工具”替代 Agent 决策。
- 合成历史包括地址变更、好评、技师相关差评、平台相关投诉、同类重复维修以及有效/异常时长样本。

### 17.2 必须演示的场景

1. **普通 P3 下单**：问题联想、地址弹窗、unit、可行时间确认、独立详情和有效分配。
2. **老客户回访**：确认历史信息、查询差评/重复维修、选择合适候选，并说明实际依据。
3. **技师执行**：出发后锁定，客户看到移动位置；开始服务、完成、反馈进入历史。
4. **客户取消**：未出发取消释放资源；已出发取消被后端拒绝；旧审批不能复活。
5. **P1 局部修复**：零扰动不可行时，在最多两张 P3 的权限内寻找可行方案并按得分执行。
6. **P0 审批**：影响其他 P2/P3 的方案进入人工审批，最新状态失效时拒绝旧方案。
7. **P2 短片段**：有效分配保留并产生备用候选；分配失效时只做零扰动补派。
8. **临时请假**：受影响未出发工单失效并恢复；执行中冲突转人工。
9. **动态休息**：工作记录达到评估条件，有空档则安排并通知；无空档则说明冲突并转人工。
10. **自主转人工**：客户没有主动请求、也没有 P0 强制审批，但因矛盾信息或超范围问题由 Agent 主动创建事项。
11. **高危险情况**：优先显示紧急联系入口并建事件，缺少普通字段也能保存草稿，不假装完成真实报警。
12. **预约协商**：客户拒绝某个时段，Agent 查询其他可行选项，不擅自修改窗口。
13. **旁路时长评估**：记录完成样本，展示 CSV 与历史基线预测误差，正式排班时长保持不变。

事件优先由真实界面动作触发；独立演示控制区可以加载场景与加速时间，不回到业务首页堆 Inject event 按钮。

## 18. 验收与测试

优先测试状态、权限、真实工具执行和跨端同步这些会导致业务错误的部分；简单文案样式不需要堆大量实现镜像测试。

### 18.1 必须通过的业务测试

- P1 允许最多两张 P3，移动 P2 或第三张 P3 被拒绝。
- P0 影响 1—5 张进入审批，超过五张或涉及其他 P1/P0 被拒绝。
- 得分恰好 70 不自动执行；目标高分但被移动订单低分也不自动执行。
- 已出发任务不被改派/取消；取消与出发并发时只有一个成功。
- 迟到按窗口结束判断，恢复目标例外不放宽其他订单窗口。
- P2 有效分配不因备用候选更优而被替换；失效分配可零扰动补派。
- 客户取消后风险、候选、等待审批与跟踪正确失效。
- 同一请假/投诉/休息事件重复投递不会重复派单或重复建事项。
- 旧版本、旧会话和过期审批不能写入最新日程。
- 动态休息与新工单并发提交不会占用同一时段；休息不打断执行任务。
- 实际服务时间不能误用出发时间，影子预测不改变正式排班。

### 18.2 Agent 验证

- 用工具结果驱动下一动作，至少展示“成功停止”“失败后改变查询/搜索”“主动转人工”三种分支。
- 工具超时和搜索耗尽不会被解释为绝对无解。
- 预算耗尽后停止并形成可处理结果，不无限循环。
- 客户、历史反馈和工具文本中的越权指令不能修改后端权限。
- 工具参数包含不存在订单或他人身份时被拒绝。
- 有模型时做少量端到端真实调用验证；无密钥时报告未验证真实模型，不能用 mock 通过宣称真实 Agent 已验证。

### 18.3 三端端到端验收

- 手机宽度完成下单、查看详情、取消或投诉。
- 技师端出发后客户和后台同步锁定及位置。
- 后台接手人工事项，客户收到站内回复。
- 地图暂停/快进、任务状态和 ETA 一致。
- 加载不同场景和重置后无旧数据、旧任务或旧动画串入。
- 现有正常主流程、语言切换和可用功能没有因改版回退。

### 18.4 演示评估

记录准时开始服务率、服务恢复结果、总通勤时间、工作负载分布、受影响订单数、人工介入、硬约束违规、工具调用数和处理耗时。

- 如比较固定工作流与 Agent，使用同一初始数据、政策、求解器、事件序列和预算口径，只改变决策编排。
- 分别报告调度效果与 Agent 行为质量，不能将更多调用或更长解释当作效果提升。
- 少量演示案例不能支持普遍性能结论；报告实际结果，不提前写“提升 xx%”。

## 19. 推荐实施顺序

### 阶段 A：基线审查和数据/状态基础

- 输出差异清单，运行现有关键测试。
- 落实必须保留的政策、状态和版本保护。
- 完成兼容迁移、客户地址、执行事件、反馈、人工事项、任务记录。

### 阶段 B：三端可操作闭环

- 客户地址弹窗和订单详情。
- 技师 Timeline、出发/开始/完成/请假/反馈。
- 后台简化、地图交互、动态位置和同步。
- 人工队列基本接手和回复。

### 阶段 C：Agent 工具与自主行为

- 接入结构化工具和运行预算。
- 历史查询、针对性追问、差评偏好、重复故障提示。
- 异常恢复、主动转人工、可行时间协商。
- 动态休息、高危险识别及模拟紧急联系。
- 任务等待/唤醒、真实活动日志。

### 阶段 D：评估和完整演示

- 时长采集与旁路预测。
- 三种负载场景及演示脚本。
- 关键规则、并发与三端测试。
- 更新运行说明、环境示例和交付报告。

持续完成全部必需范围；如确有外部服务阻塞，给出可工作的适配器和明确限制，不以缺少密钥为由停止所有本地工作。
