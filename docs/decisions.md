# Decisions

Two sections: **confirmed business rules** (from `docs/project-brief.md`, not changeable here) and **engineering defaults** (chosen by the implementer, with reasons; adjustable without changing policy).

## A. Confirmed business rules (implemented as specified)
- Priorities: normal base P3, simulated-paid base P1; effective = most urgent(base, risk); paid may rise to P0 by risk, never drops below P1.
- Authority: P3/P2 change no other order; P1 may move ≤2 undeparted P3; P0 may move ≤5 undeparted P2/P3; nobody moves EN_ROUTE/ARRIVED/IN_PROGRESS; P1 never moves P0/P1/P2; P0 never moves P0/P1.
- Auto threshold strictly `> 70` on `decision_score = min(match_score of new/changed assignments)`; 70.0 goes to review.
- P0 with 1–5 affected always manual; P0 zero-affected low score manual; over-limit plans are alerts, never approvable.
- Technician cancel: `<30` min to window_end → P0; `30..120` inclusive → P1; `>120` → P2 (then merged with other risks and paid floor).
- Customer cancel only before departure; ARRIVED counts as departed. Complaint of attitude/quality → manual queue, no priority change.
- Complexity and duration always come from the catalog snapshot on the order; no LLM estimation, no added buffers.

## B. Engineering defaults (with reasons)
| Topic | Decision | Why |
|---|---|---|
| Stack | FastAPI + SQLAlchemy/SQLite, React + Vite + Tailwind | brief default; no existing code to reuse in this folder |
| Ports | backend 8100, frontend 5174, both bound to `127.0.0.1` explicitly | 8000/5173 are used by the V1 prototype on this machine; Vite's default `localhost` bind listened on IPv6 only, so `http://127.0.0.1:5174` failed |
| Scenario day | 2026-09-15, sim start 08:30 SGT | fixed day makes the fixture reproducible |
| Time model | DB naive UTC; API ISO with `+08:00`; solver integer minutes from local midnight | brief §6.3 |
| Departure timing | Just-in-time departure (`departure = service_start − travel`), leaving idle time at the previous stop; if JIT travel would cross a break, leave before the break and wait at the customer | avoids hours of waiting at customers; still satisfies "wait for window_start" |
| Breaks | travel and service may not overlap breaks/unavailability; waiting may (the tech rests while waiting) | breaks are a simulated company rule, not a legal claim |
| Shift end | service must end by shift end; return trip to base is not required | simpler; documented |
| Unchanged assignments | treated as facts in validation (no window/shift re-check); only sequence consistency is checked | otherwise a predicted-late old order would block unrelated inserts |
| Overdue orders | `recovery_target=True` for any undeparted order past `window_end`; window constraint becomes `start ≥ now`; still only movable as its own P0 target because it is P0 by risk | brief §8.4 |
| Search | feasible insertion for all qualified techs + bounded local search: relocate one movable order elsewhere / reorder on the same tech, then insert the target; capped by `solver.max_relocate_candidates` and a time budget | enough for 2/5-affected repairs; no global optimality claimed |
| Execution pick | among approvable candidates, highest decision score (ties: earlier start, fewer affected); auto only if that candidate's policy result is AUTO, else everything goes to review | keeps "best plan" and "auto rule" consistent |
| Scoring weights | 30/25/20/10/15; scales: travel 60 min, response 120 min, shift 60 min, affected reference 2; a re-assigned old order gets a 0.5 own-change penalty | see `docs/scoring.md`; calibrated so zero-disturbance plans beat marginally better travel |
| Initial batch | greedy priority → deadline order; committed orders are pinned; batch placements may still be re-timed by later insertions; any low score → whole batch to review | brief §15.3 |
| Candidate expiry | 30 sim minutes (raised from 5 after the demo regenerated review cards every 5 minutes of advance); also expired when the active schedule version changes; recomputed automatically on the next scan | brief §15.1 |
| Dispatch dedupe | `last_dispatch_key = priority|schedule_version|order_version|tech versions hash`; a scan re-dispatches only if the key changed | brief §13.3 (no repeated approvals/notifications) |
| Multi-order technician cancel | facts updated for all orders first; targets processed most-urgent-first; any plan with affected>0 forced to manual in that batch | brief §10.1 (no limit circumvention through combinations) |
| Concurrency | single process; all mutations under one re-entrant lock; background loop uses the same lock | brief §20 |
| Route fixture | 18 preset Singapore locations, deterministic asymmetric minute matrix (`scripts/generate_fixtures.py`), straight-line schematic geometry | offline demo/tests; asymmetry prevents symmetric assumptions |
| Locations | `fixture` mode: preset areas only (map pin snaps to nearest preset, told to the customer); `osrm`/`estimated`: exact map-picked points become `Location` rows (`pt_<hash>`, deleted on reset) and join the travel matrix | the fixture matrix cannot price arbitrary coordinates honestly; a road-network provider can |
| OSRM time adjustment | `ceil(free-flow × 1.25) + 3 min` (configurable) | OSRM has no live traffic; a plain free-flow ETA would be optimistic, and the allowance covers parking/building access — an engineering default, not measured |
| Route degradation | any real-provider failure degrades the whole round to `estimated` (haversine), labelled DEGRADED | estimated can price map pins; fixture cannot |
| Route cache | OSRM matrices cached on disk by snapshot id (sorted location ids + base URL + factor/base); leg geometry cached in memory | restarts/resets never re-query; public demo server stays within polite use |
| Notifications | in-app rows with `delivery_mode=simulated`, dedupe keys | brief §2.3 |
| Reset | deletes scenario-scoped rows and increments `scenario_generation`; catalog & locations kept; old async results check generation | brief §17 |
| Approval staleness | a pending plan is stale when the schedule version moved or any order it touches changed version; technician facts are re-validated (timing, availability) instead of version-compared, so unrelated execution events do not expire plans | otherwise every completion elsewhere expired pending reviews |
| Over-limit plans | persisted as `OVER_LIMIT` (alert, no approve button) only while the target has no approvable plan; when another plan of the same run auto-commits they are stored as `SUPERSEDED` | a stale "exceeds authority" card next to an already-dispatched order confused the dispatcher |
| Same-event staleness | inside one technician_unavailable event, targets are processed most-urgent-first; if a later auto-commit moves the schedule version, pending plans generated earlier in that event are expired and recomputed before the event returns; the UI also recomputes automatically when an approve returns `plan_expired / schedule_changed / facts_changed` | never commit a plan computed against old facts, but do not make the dispatcher click "recompute" for a race the system created |
| Review cards | single column in the right panel (5/12 of the width), key-value grid, diff table with `counts` column, comparison table when ≥2 candidates | the earlier 3-column layout squeezed cards to ~130 px |
| Geocoding | provider chain OneMap → Nominatim (`GEOCODE_MODE=auto`), memory + disk cache keyed by normalized query; an address-looking hint (digits / street words) goes to the geocoder before area-name matching; exact vs ambiguous decided by "single hit" or "the only hit containing every typed number", landmarks by dominant relevance; identical labels deduplicated | coordinates only ever come from a provider or the preset table; OneMap needs an account the user must create |
| Stored candidate rows | every assignment that differs from the base in any field (incl. travel-only successors), flagged `changed` when tech/start differ | approval must re-validate exactly the scored plan |
| Offline evaluation | in-memory harness on synthetic worlds from the real catalog; departed tasks locked / finished tasks completed when time advances; manual plans counted as approved | fair comparison from the same base; see `docs/evaluation.md` |
| LLM providers | `openai_compat` (openai SDK against any `/v1` endpoint; JSON mode with prompt-only fallback; robust JSON extraction; Pydantic validation; ids guarded against the catalog) and `anthropic` (SDK structured outputs). mock returns the same schema. Chosen by the user: DeepSeek via ModelScope | provider is swappable without touching UnderstandingAgent/chat logic |
| LLM in tests | `tests/conftest.py` forces `LLM_MODE=mock` regardless of `.env` | tests stay offline and deterministic |
| Chinese area names | alias table (后港→Hougang …) in `resolve_location`; coordinates still only from presets | real model returns verbatim Chinese hints |

## V3 decisions (2026-09-16)

| Topic | Decision | Why |
|---|---|---|
| Migration | additive only: `ALTER TABLE ADD COLUMN` for missing columns, new tables via `create_all`, versions in `schema_migrations`; `address` back-filled from the order's location with `unit_pending: true` | V2 data keeps working; nothing is rewritten or guessed (a missing unit stays visibly missing) |

| Feasible windows | `propose_windows`: 30-min steps 08:30–17:00, 90-min windows, zero-disturbance insertion trials (`allow_relocate=False`, 400 ms), returned with technician + earliest start; proposals are never reservations (re-validated on submit) | brief §7.2 / §8.2: only offer what is currently feasible without moving others |
| Preferences | rating ≤ 2 on a technician → ranking penalty (0.4 / 0.6 × `PREFERENCE_WEIGHT` 8) in candidate choice only; hard exclusion only per order and only when the customer asks; when all feasible windows use the disliked technician the chat says so | brief §8.3: "prefer another person in comparable plans; explain when there is no alternative" |
| Repeat-fault hint | completed orders of the same customer (or the same precise `pt_*` point) in 90 days, same trade; worded "similar repair record"; shared preset areas never match | no device identity → never claim "the same unit failed again"; a preset area is many households |
| Human cases | three sources; idempotency key + open-case merge (evidence appended, urgency escalated, `escalations` counter); `plan_approval` cases created with every manual decision and auto-resolved by approve/reject; `execution_interrupted` cases for interrupted locks; the assistant is paused for a customer with an open case | one queue for everything a human must decide (brief §9); the review queue and the human queue never disagree |
| Agent runtime | tools are the only interface; `ToolResult` with reason codes; role gating + JSON-schema arg checks; budgets 12 / 3 / 2 per wake-up; budget exhaustion and `no_solution` always end in `flag_for_human` with the trace; tasks wait on customer answers / human resolutions and are woken explicitly; one live scheduling task per order (no re-investigation per version bump while waiting) | brief §10–§11; no loops, no silent giving up, no cost explosion when the fast path fails repeatedly |
| Model authority | `ModelPolicy` returns one JSON action; `submit_plan` only accepts stored plan ids and re-validates through the PolicyEngine; `urgency` written by the model is normalised to the known scale | a model can propose, never commit or widen authority |
| Fast path first | ordinary orders never create a task; tasks only on `UNRESOLVED`, rest evaluation, or human wake-up; mock tasks run inline, real ones in the worker thread | brief §10.5 latency: one request for the common case |
| Dynamic rest | no fixed lunch in scenarios; thresholds 180 (evaluate) / 60 before (pre-evaluate) / 240 (escalate) / 30-min default / 15-min slot step / 90-min lookahead; `submit_break` re-validates zero disturbance under the current schedule version inside the transaction; declared rest is a fact that the risk scan checks afterwards | brief §7.3; rest must never silently move customers, and a technician's own declaration must never be refused |
| Execution facts | `ExecutionEvent` per transition with actor; anomalies flagged (early/late vs window and plan, service much shorter/longer than baseline) and never rewritten; `sim_mode` manual ⇒ the simulator refuses to drive that technician (single driver) | brief §12: recorded facts over plan-compliant fiction |
| Duration data | actual = start → complete; quality `ok / missing_time / negative / outlier`; shadow prediction = median by problem on a time split, ≥ 5 samples, else CSV baseline; MAE reported; scheduling durations remain the CSV | brief §13: learn without changing the official basis until evaluated |
| Safety | deterministic triggers with negation and past-tense guards, plus an optional model `safety_concern` (≥ 0.7) — both create an incident + critical human case; emergency numbers filled only after verification against official pages (gov.sg, cityenergy.com.sg) with the source stored next to the number; the UI opens a `tel:` link or records a demo assistance request | brief §11.4: never report on the customer's behalf, never invent a number |
| Positions | interpolated along the cached OSRM leg geometry by elapsed / planned travel; labelled "simulated: route geometry + sim clock"; customer tracking only while their own order is departed | brief §14: honest about what a position is |
| Dashboard | 4 KPIs, engineering counters behind "more"; Inject Event and scenario loading in a Demo-controls drawer; implementation facts, duration report and tool traces in a Dev drawer | brief §13.2: a dispatcher screen, not an engineering console |
