# 1. 一个业务故事

**我们在解决什么问题。** 一家有 10 名技师的上门维修公司，每天接 20–30 张工单。真正消耗人力的不是把单排出来，而是排完之后的变化：技师临时请假、客户催单、上一单超时。每一次变化，都要有人重新想一遍"谁能去、去了会不会耽误别人、要打几个电话"。

**谁在承受它。** 这家公司通常没有专职调度岗，这件事落在店主或一名文员身上。他一边接电话一边在表格上找人，凭经验判断来不来得及，改完之后没有任何记录。

**Agent 创造什么价值。** TechSched 把"听懂客户、判断能不能排、算出改动会影响谁"这三件事交给系统：常规工单全程零人工；发生变化时，系统在企业设定的权限范围内重排，并把结果做成一张带决策分、受影响清单和逐行差异的卡片交给调度员——他的工作从"重新推演"变成"批准或拒绝"。超出权限或无解的情况，系统不会静默失败，而是带着已经尝试过的动作转人工。

**我们期待什么可衡量的结果。** 调度人力占用下降、变更响应时间下降、准时上门率上升、人工介入比例可被逐月观测；而在系统自己已经能测的部分，**已提交方案的规则违规数恒为 0** [实测]。

# 2. 问题与机会

## 2.1 目标客户与相关方

| 相关方 | 在这件事里的角色 | 关心什么 |
|---|---|---|
| 企业主 / 文员（调度） | 接单、派工、处理变更 | 今天有没有单排不进去、哪些要我拍板、改动会不会得罪客户 |
| 维修技师 | 执行上门服务 | 下一单在哪、几点出发、门牌号、为什么临时插单 |
| 报修客户 | 提出需求、等待上门 | 什么时候有人来、来的人会不会修、能不能改期或加急 |
| 企业主（经营） | 看结果 | 人力占用、准时率、每单成本、能不能多接单而不加人 |

目标客户画像：新加坡本地、技师 5–20 人、日均工单 15–40 张、覆盖两个以上工种的上门维修公司。这一规模属于新加坡官方定义的中小企业范畴（年营业额不超过 1 亿新元或雇员不超过 200 人）。

## 2.2 今天的工作流程与痛点

| 痛点 | 具体表现 | 经营后果 |
|---|---|---|
| 可行性靠估计 | 排班时无法确认技师是否来得及、技能是否够 | 迟到与返工，客户投诉 |
| 变更没有边界 | 为救一张急单动了几个客户的约定，全凭当时判断 | 老客户体验受损，且无法事后复盘 |
| 决策无法追溯 | 改完就改了，没有版本与理由 | 纠纷时说不清，经验无法沉淀 |
| 信息不完整 | 地址缺单元号、问题描述不清 | 技师白跑一趟 |
| 质量不可复制 | 调度质量等于那个人当天的状态 | 无法随团队规模扩展 |

## 2.3 为什么值得解决

- **频率高。** 变更不是偶发事件。在我们构造的评测场景中，一天内包含新单插入、付费加急、技师取消等 6 类事件 [实测：每个随机种子 6.1 个事件]；真实经营中，技师请假、客户改期、路上延误属于常态。
- **代价直接。** 一次处理不当的变更，代价是一个客户的时间、一名技师的半天，以及一次可能的差评。
- **不解决就无法扩张。** 调度能力绑定在一个人身上，这家公司增加到 20 名技师时，这个人会成为瓶颈。

## 2.4 机会

现场服务管理软件是一个持续增长的细分市场，多家研究机构对 2026 年全球规模的估计在 56 亿至 61 亿美元之间，复合年增长率约 14%–15%。但这类系统的定价与实施复杂度主要面向中大型企业，**5–20 人的维修公司通常仍在用电话加表格**。大语言模型第一次让"把客户随口说的一句话变成结构化工单"变得便宜，使得面向这一规模客户的产品在成本上成立。

# 3. 解决方案（业务视角）

## 3.1 系统做什么

三个终端，一套后台：

| 终端 | 谁用 | 做什么 |
|---|---|---|
| 客户端 | 报修客户 | 对话报修、确认地址、选一个**确实排得进去**的时间窗、跟踪进度、加急或改期 |
| 技师端 | 维修技师 | 看下一单（含门牌单元与客户历史）、上报执行状态、请假、申报休息 |
| 调度工作台 | 企业主 / 文员 | 看当日排班与风险、审批需要拍板的方案、处理人工队列 |

后台由三个 Agent 与一套确定性调度引擎组成。**关键的产品判断是：模型负责理解与选择，规则负责可行性与授权。** 技能匹配、维修时长、能不能自动执行、能动几张单，全部由代码和企业自己的配置决定，不由模型判断。

## 3.3 人留在哪里

自动化的边界是显式的、可配置的，而不是靠模型自觉。

<figure class="fig fig-chart">
<img src="handbook-assets/bp-decision-routing.svg" alt="图 2　每一个调度决定的去向">
<figcaption>图 2　每个调度决定的三种去向及其触发条件。规则写在一个配置文件里，企业可以调整边界，但任何配置都无法绕过可行性校验与权限上限。</figcaption>
</figure>

对企业主而言，这意味着三件事：

1. **自动化程度可调。** 想更保守，把自动执行的分数门槛调高，更多方案就会进审批。
2. **高风险决定一定有人签字。** 只要一个紧急工单需要动到其他客户的约定，无论系统算出的分数多高，都必须调度员批准 [实测：由策略引擎的裁决顺序保证，有测试覆盖]。
3. **系统不会假装能处理。** 无可行方案时它会交出一份带证据的人工事项，而不是沉默或反复重试。

# 4. 业务价值

按 Agent 在六个方向上创造的价值分别说明。标注 [实测] 的是系统已经具备并可验证的行为，标注 [假设] 的是据此推导的经营影响，需在试点中验证。

| 方向 | Agent 做了什么 | 对经营的影响 |
|---|---|---|
| **生产力** | 常规工单从客户描述到派单完成，全程无人参与 [实测：快路径在一次请求内完成，不创建人工任务] | 调度人员从"每单都要经手"变为"只处理例外" [假设：可释放约 60% 的调度时间] |
| **成本** | 调度决策由确定性代码完成，模型只参与对话与分类 [实测] | 模型调用成本随**对话数**增长，不随排班复杂度增长——工单越多越复杂，单位成本反而摊薄 |
| **收入** | 加急是一个可收费且后果透明的产品功能：付费前告知会移动几张普通单、是否需要调度员确认 [实测] | 新增一条与调度能力直接挂钩的收入线 [假设] |
| **服务** | 客户拿到的是"09:30–11:00，Bala 预计 10:33 到"，而不是"下午"；被改期时收到说明 [实测] | 减少催单电话与投诉 [假设] |
| **风险** | 硬约束与权限由独立校验器复查，越权方案连审批入口都没有 [实测：两套评测中已提交方案的违规数均为 0] | 减少"排了但做不到"的承诺与随之而来的纠纷 |
| **规模** | 同一套规则处理 12 单、20 单与 32 单的场景，求解耗时均值 0.9 毫秒 [实测] | 接单量增长不需要等比增加调度人力 |

# 5. 影响与可衡量成果

## 5.1 KPI 设计

每个 KPI 都指明了在系统里从哪里读取，以便试点期间直接取数，而不是靠主观评价。

| 业务成果 | KPI | 基线（当前做法） | 目标 | 系统中的取数位置 |
|---|---|---|---|---|
| 减少人工作业 | 常规工单的人工介入比例 | [假设] 100%，每单都要人经手 | < 10% | Agent 记分卡 `autonomy.rate_pct` |
| 提升生产力 | 单次变更的处理时间 | [假设] 约 15 分钟（重新推演 + 电话） | < 3 分钟（审批一张卡片） | 审批事件时间戳（方案生成 → 批准） |
| 改善客户服务 | 原时间窗准时开始率 | [假设] 无系统记录，凭投诉感知 | 逐月可见并持续提升 | 评测与执行事件 `on_window_rate` |
| 降低风险 | 已提交方案的规则违规数 | [假设] 不可知（无校验机制） | 恒为 0 | 评测 `hard_or_authority_violations` [实测：已为 0] |
| 提升响应 | 紧急工单未服务数 | [假设] 无口径 | 逐月下降 | 评测 `urgent_unserved` |
| 支撑扩张 | 每名调度人员可支撑的技师数 | [假设] 约 10 人 | 20 人以上 | 技师数 ÷ 调度 FTE |

## 5.2 价值测算示例

以一家 10 名技师的公司为例。**每一项输入都标注了来源**，便于企业用自己的真实数字替换后重算。

| 输入 | 取值 | 来源 |
|---|---|---|
| 技师人数 | 10 | 假设（目标客户画像） |
| 日均工单 | 25 | 假设（与演示场景 8 技师 20 单的密度一致） |
| 每月工作日 | 26 | 假设 |
| 当前调度投入 | 每天 2.5 小时（约 0.3 FTE） | 假设 |
| 其中常规派单与确认占比 | 60% | 假设 |
| 常规工单的人工介入 | 0 | **实测**（快路径不创建人工任务） |
| 单次变更处理时间 | 15 分钟 → 3 分钟 | 前者假设；后者为"审批一张卡片"的界面操作估计 |

**推导结果**：调度投入由每天 2.5 小时降至约 0.9 小时，折合每月约 42 小时。按假设的调度人员综合时薪 S$18 计算，约为**每月 S$750 的人力释放**；更重要的是，这部分时间原本无法用于接单与客户维护。

> 该测算是一个**模型**，不是承诺。它的作用是把主张拆成可以逐项质疑的输入。试点的第一项工作就是用真实数据替换上表，并在 4–8 周后对照 5.1 的 KPI 取数。

# 6. 可行性

## 6.1 维持方案所需的数据与知识

这是落地成本中最容易被低估的一项，因此单独说明。

| 需要什么 | 谁来维护 | 工作量 | 我们的处理 |
|---|---|---|---|
| 维修问题库（工种、问题、复杂度、标准时长） | 企业的技术负责人 | 初次整理一次，之后按季度增补 | 一个 CSV 文件，46 条即可覆盖 10 个工种；导入时报告实际表头、字段映射与错误行，**冲突的重复键会中止导入而不是猜测** |
| 技师名册与技能等级 | 企业主 | 初次录入，人员变动时更新 | 一个 JSON/表单；技能等级是派单硬条件，**填错会直接表现为派不出单，不会悄悄降级** |
| 业务规则（优先级、权限、审批门槛、休息阈值） | 企业主 | 初次设定，之后很少改 | 集中在一个配置文件，改规则不需要改代码 |
| 客户与历史 | 系统自动积累 | 无 | 完成的工单自动形成历史与偏好 |

**问题库缺失时系统拒绝建单，不会退化成编造的目录** [实测]。这是一个刻意的选择：宁可不工作，也不要给出一个基于臆测时长的承诺。

## 6.2 系统、工具与 API

| 能力 | 当前实现 | 是否已联调 |
|---|---|---|
| 大语言模型 | provider 层可替换：OpenAI 兼容端点 / Anthropic SDK / 离线 mock | 线上运行中（模型标识 `global.anthropic.claude-sonnet-4-5-20250929-v1:0`，经 OpenAI 兼容网关） |
| 路网与通勤时间 | OSRM（可用公共服务器或自建） | 已联调 |
| 地址解析 | OneMap（新加坡邮编与组屋门牌）→ Nominatim | 已联调（含真实 OneMap 账号） |
| 通知 | 站内通知，标注为模拟 | 未接真实短信通道（试点项） |
| 支付 | 模拟支付事件 | 未接真实支付（试点项） |

三个 provider 返回同一套数据结构，因此**更换模型或路网供应商不需要改动业务逻辑**——这既是成本控制手段，也是供应商锁定风险的对冲。

## 6.3 人工介入与升级

人工介入不是兜底，而是产品的一部分，有明确的触发条件与交接标准：

- **三个来源**：客户主动要求、策略规定必须人工、Agent 主动升级。三者进同一个队列，可接管、回复、关闭；客户有未关闭事项时助手暂停，不再做任何排班承诺 [实测]。
- **交接标准**：Agent 升级必须同时给出证据引用、已尝试的动作与建议的下一步；缺任意一项不构成有效升级 [实测：由工具契约强制]。
- **不会重复打扰**：同类未关闭事项自动合并，追加证据并提升紧急度，而不是新建一条。

对企业的意义是：**人工队列的长度是一个可管理的经营指标**，而不是一堆无法归类的例外。

## 6.4 部署与运营需求

| 项目 | 现状 |
|---|---|
| 部署形态 | 单进程后端 + 静态前端，nginx 反向代理 + systemd；已在线运行于 https://byyyc.com/techsched/ |
| 运行状态 | `https://byyyc.com/techsched/health` 返回当前模型、路线、地理编码与策略版本，不含任何密钥 |
| 部署动作 | 一个脚本完成：装依赖 → 构建前端 → 同步静态文件 → 重启后端 → 健康检查 |
| 离线可运行 | 默认配置为离线 mock 模型 + 内置通勤矩阵，**克隆即可运行**，便于客户在不接外部服务的情况下先试 |
| 模型成本结构 | 调度本身不调用模型，模型只用于对话与投诉分类。**成本随对话数增长，不随工单数或排班复杂度增长** |

模型的实际 token 消耗尚未埋点计量，这是试点第一周要补的一项，不在此处给出估算。

## 6.5 风险与暴露面

| 风险 | 评估 | 缓解 |
|---|---|---|
| 模型输出不可控 | 模型无法设置优先级、时长或权限——它没有对应的工具 [实测] | 结构性隔离优于提示词约束；客户文本被声明为数据 |
| 外部服务中断 | 模型或路网不可用 | 自动降级并在界面标注：模型降级为规则实现，路网降级为直线估算 [实测] |
| 错误承诺 | 给客户一个做不到的时间 | 时间窗只展示当前确实可行的；提交时再次校验，不静默接受 [实测] |
| 安全事件（燃气、触电） | 客户描述危险情况 | 停止排班、给出已核实的官方电话、生成 critical 人工事项；**不代客报警、不自动拨号** [实测] |
| 数据合规 | 客户地址与电话 | 当前为合成数据；生产前需补充数据留存策略与分角色权限（见 7.3） |
| 供应商锁定 | 依赖单一模型厂商 | provider 层可替换，已实现三种 |

# 7. 可扩展性

## 7.1 更多用户与交易量

- **算法侧有余量**：三个负载场景（12 / 20 / 32 单）下求解耗时均值 0.9 毫秒、最大 33 毫秒，预算为 3–5 秒 [实测]。当前瓶颈不在求解。
- **架构侧有明确限制**：当前为单进程部署（全局锁），这是原型阶段的有意取舍。转向多进程需要把状态锁换成数据库层的并发控制，属于已知的工程项而非架构重写（见技术设计文档 9.L6）。
- **成本侧是有利的**：调度不消耗模型调用，工单量增长不推高模型成本。

## 7.2 跨职能扩展

同一套"可行性校验 + 权限边界 + 人工审批"的结构，可以复用到维修之外的排程场景：保洁与安装、设备巡检、家政服务。需要替换的是问题库与技能定义，不是调度引擎。

更近的一步是在同一家客户内横向扩展：库存与配件（派单时校验配件是否在车上）、工时与结算（执行事实已经在记录）。

## 7.3 监控、安全与治理

| 维度 | 现状 | 生产前需补 |
|---|---|---|
| 可观察性 | 三层记录：编排阶段、Agent 逐步轨迹、排班版本链；每次决定可回放到版本与理由 [实测] | 接入统一日志与告警 |
| 运行质量 | Agent 记分卡：自主率、单任务成本、无效调用比例、交接完整率 [实测] | 设定阈值告警 |
| 鉴权 | 演示用身份选择器，**不是认证系统** | 真实身份认证与分角色权限 |
| 审计 | 决策链已完整留存 | 留存期限策略、导出与合规审计 |
| 多租户 | 未实现 | 数据隔离与按企业计费 |

# 8. 商业模式与推进

## 8.1 收费模式

| 模式 | 说明 | 适配的客户 |
|---|---|---|
| 按技师席位订阅 | 每技师每月固定费用，含调度、客户端与技师端 | 主力模式：客户规模与价值直接相关，且技师数是企业自己清楚的数字 |
| 加急功能分成 | 客户付费加急的收入按比例分成 | 与我们创造的价值直接挂钩；加急能成立的前提正是系统能算出"确实更早" |
| 一次性接入服务 | 问题库整理、技师名册导入、规则配置 | 降低首次落地门槛 |

定价需在试点后确定，本文不给出具体数字——在没有真实 KPI 基线之前，任何定价都是猜测。

## 8.2 落地路径

1. **一家试点客户，4–8 周。** 目标不是签单，是拿到 5.1 那张 KPI 表的真实基线与改善幅度。
2. **以问题库为切入点。** 整理问题库对企业本身就有价值（标准工时、报价依据），且是系统运转的前提，适合作为第一次接触的交付物。
3. **保留全部审批点。** 试点期不追求提高自动化比例，先让调度员建立对系统判断的信任，并按周复盘误判。
4. **用同一套指标复盘。** 自主率、人工介入比例、准时率逐周出数，作为是否进入生产阶段的决策依据。

# 9. 主张与演示证据对照

演示视频与本文必须讲同一个故事。下表把每条业务主张对应到演示中的具体片段与系统中的可验证位置。

| 本文主张 | 演示中的证据 | 系统中可验证的位置 |
|---|---|---|
| 常规工单零人工介入 | 客户在 App 报修 → 确认 → 工单直接进入已分配；时间轴上其他技师的任务一个都没有变化 | 工单状态为 `ASSIGNED`，未创建 Agent 任务 |
| 高风险决定必须有人签字 | 技师请假 → 紧急工单需要移动一张普通工单 → 审批卡片出现，**即使分数高于门槛也无法自动执行** | 策略引擎裁决为 `manual`；审批队列 |
| 改动的代价是透明的 | 审批卡片上显示决策分、受影响 1/5、逐行差异（某单由 A 改派给 B） | 候选方案的差异表与受影响清单 |
| 付费只买规则允许的东西 | 客户加急 → 付费前告知会移动几张普通单、是否需要调度员确认；不比空闲时段更早时不展示付费选项 | 加急试算与策略裁决 |
| 系统不会静默失败 | 稀缺场景下一张排不进去的工单 → Agent 调查 → 提出备选时间窗 / 带证据转人工 | Agent 推理时间线与人工队列 |
| 每个决定可回放 | 推理时间线逐步展示：为什么这一步、调用了什么、结果如何、耗时多少 | 三层记录与排班版本链 |

| 编号 | 假设 | 用在哪里 | 如何验证 |

| A4 | 调度人员综合时薪 S$18 | 5.2 价值测算 | 客户实际成本 |

## 10.2 系统当前的限制

| 编号 | 限制 | 影响 |
|---|---|---|
| L1 | 演示数据为合成数据；通知与支付为模拟 | 试点前需接入真实通道 |
| L2 | 问题库当前 46 条 / 10 工种 | 覆盖率直接决定可自动处理的比例 |
| L3 | 路网时间不含实时路况，系数为工程默认值 | 需用实际出发到达时间标定 |
| L4 | 求解器为启发式，不保证全局最优；单日单区域 | 跨日与多区域排班未实现 |
| L5 | 单进程部署；身份选择器不是认证系统 | 生产前需补多进程与真实鉴权 |
| L6 | 评测数据来自合成世界 | 不构成对真实业务收益的量化结论 |
